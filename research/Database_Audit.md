# Database Audit (Phase 4)

Scope inspected: `app/models/*.py` (User, Profile, AssessmentSession, AssessmentResult, GuestProfile, GuestAssessmentSession, GuestAssessmentResult), all 6 Alembic migrations, `app/config.py` (Supabase Postgres via `DATABASE_URL`, plain SQLAlchemy — no Supabase-specific features like RLS in use), `app/services/assessment_service.py`, `app/routes/api.py`.

## Already stored
- **Identity/auth**: `users` (email, password_hash, is_active) — no CCI-relevant gaps.
- **Permanent profile**: `profiles`/`guest_profiles` — full_name, age, gender, education, dominant_hand, native_language. Matches every demographic covariate the sourced papers actually validated (see Demographics.md) except family history.
- **Per-session context ("Today's Check-In")**: `assessment_sessions`/`guest_assessment_sessions` — sleep_quality, stress_level, hours_slept, caffeine_today, medication, current_mood, wearing_glasses, distractions. This is already the exact "temporary factors" list Phase 6 requires (stress, mood, caffeine, distractions, medication) — correctly scoped as session-level, not profile-level, and never currently blended into any score (nothing reads them downstream yet — that's a Phase 6 code gap, not a schema gap).
- **Versioning**: `assessment_version`, `algorithm_version` (session-level), `game_version` (per-result) — already exists specifically as "Sprint 8 prep" for CCI work per the code's own comments. This is the right place to stamp which CCI formula version scored a given result once Phase 6 ships.
- **Research metadata**: `session_metadata` JSON — browser/device/viewport/timezone/resume counts/idle time/completion mode/attempt number. Already research-grade.
- **Per-module results**: `assessment_results`/`guest_assessment_results` — domain, score, accuracy, average_time, rating, and a flexible `raw_data` JSON column. Every metric identified as "add" in Master_Metrics.md (NPS inputs, Corsi span/rounds, Processing efficiency, per-angle-band RT for rotation-rate) **is already sitting in `raw_data` today** — confirmed by reading memory.js/attention.js/executive.js/processing.js/visual.js `CT.writeSession()` calls directly. Nothing needs to be collected that isn't already collected.
- **Guest/auth parity**: guest tables are structurally identical mirrors, deliberately separate (never a nullable user_id on the authenticated tables) — sound design, no changes needed.
- **Integrity**: check constraints on score/accuracy/duration/age ranges, unique constraint on (assessment_id, domain), composite index on (user_id, status) for the hot dashboard/resume query. All appropriate, nothing missing.

## Missing
- **Family history.** Requested explicitly by the brief as a temporary/contextual factor; genuinely absent from every table (verified via grep — zero hits outside CSS class-name false positives). See Demographics.md.
- **A structured place for CCI output.** Notably: the *very first* migration (`20f324be9f40`) already had `cci` (Float) and `risk_level` (String) columns on `assessment_sessions` — and they were dropped as **dead columns** in migration `99f8455a6a47` because nothing ever computed or wrote to them. This is direct evidence a single flat float is the wrong shape: Phase 6 requires raw → normalized → domain scores → confidence → overall profile, which cannot live in one number. Don't repeat the same mistake by re-adding a bare `cci` float.

## Recommended (with justification)
1. **Add `family_history` to the check-in field set** (`AssessmentSession`/`GuestAssessmentSession`), same enum pattern as the existing `distractions` column (e.g. `none`/`some`/`significant`, or a simple boolean) — additive, nullable, one migration, matches the exact precedent already set by migration `9d77dfce01ee`. *Justification*: explicitly requested by the brief; no sourced paper quantifies it, so per Phase 6 rules it can only ever affect confidence/interpretation, never a raw score — same treatment as the other 8 check-in fields already in the schema.
2. **Do NOT add a persisted CCI/domain-score column at all — compute on read.** Every input the CCI needs (raw_data, profile demographics, check-in context) is already persisted. The CCI formula is pure math over data that already exists, `algorithm_version` already exists to stamp which formula version is "live," and recomputing at dashboard-read time means an algorithm improvement instantly applies to all historical sessions with zero backfill migration. Given the 2-day window, this avoids: a schema migration, a backfill script, and a stale-cache bug class entirely. *Justification*: this is exactly the failure mode the dropped `cci`/`risk_level` columns already demonstrated — a persisted derived value nobody kept in sync went dead. Compute-on-read in `assessment_service._shape_dashboard_payload()` (already the single chokepoint every dashboard read passes through) instead.

## Not needed
- No new raw-telemetry columns or new JSON keys — confirmed everything Master_Metrics.md calls for already exists in `raw_data`.
- No dedicated norms/reference table — age-band correction factors (Executive's U-shaped curve, Attention/Memory's linear ones) are static constants, better as a small Python module (same pattern as `core/versions.py`) than a DB table needing seed/migration machinery for a 2-day scope.
- No analytics/warehouse table — `session_metadata` JSON already covers research-readiness needs.
- No schema change for guest tables beyond mirroring #1 above — they already mirror the authenticated schema field-for-field.
